# ADR 0010：Jules 受控工作包与分阶段扩容

- 状态：已接受
- 日期：2026-10-23

## 背景

维护者已同意扩大 Jules 实现职责。账户额度足以试运行更多任务，但额度不能证明任务可独立交付，也不能替代最终复核。官方能力包含功能开发、独立 VM、环境快照及任务反馈；本仓库需要把权限扩大与交付能力验收分开。

## 决策

- 局部替代 [ADR 0008](0008-scoped-bot-autofix.md) 的 Jules 文档/测试小任务范围：保留 Documentation、Tests，并增加逐工作包准入的 Tooling。实现、测试和必要文档可作为一个交付目标，不为消耗额度拆分用例。
- 类别、精确路径与数量的机器规则只在 `bot-dispatch.yml` 维护；当前 Tooling 先准入离线测试结果汇总工作包。其它工具及产品模块须经主执行者评估和独立规则变更后开放，不自动放开 `scripts/**` 或 `src/**`。
- 沿用 Small task for Jules 表单和 workflow，校验双方写权限、独立验收、文件占用及在途容量；增加的 GitHub 权限仅为只读 PR 元数据。Jules App 写权限不因此成为文件级沙箱。
- 主执行者负责契约、依赖顺序、高风险代码、实际 diff 与验证。Jules 负责已授权工作包的实现和范围内返工；一个分支一个写入者，重叠文件不并行派发。
- 高风险排除、CodeRabbit 规则、人工合并、发布授权、禁止机器人递归派单继续沿用 ADR 0008。Jules 不得修改自身派单/环境/治理规则或降低断言来获得通过。
- 先建立轻量环境和小批量交付样本，再按净节省时间、首次验收通过率、越界情况和审查积压扩容。数字阈值与回退流程见[操作约定](../bot-automation.md)，不以用满供应商额度为目标。
- API/CLI 调度属于后续评估，不在本决策中建立第二写入入口；未来如需强制计划审批，应验证 `requirePlanApproval` 等实际入口行为，不能把网页计划界面当成硬门禁。

## 后果

可让 Jules 承担完整低风险实现，同时增加主执行者的任务准备与复核责任。GitHub Issue/PR 占用检查是保守调度，不是真实 Jules session 计数，也无法观察未公开的本地编辑。未确认停工前不得通过关闭 Issue 或移除标签释放占用。端到端与环境快照验收仍归 [RISK-008](../RISK_REGISTER.md#risk-008p1机器人自动写入与自动派单端到端未验收)。

## 替代方案

- 永久只做文档小修：不能充分转移实现工作，不采用。
- 开放全部源码并直接跑满并发：缺少独立验收和审查容量证据，不采用。
- 同时启用 Issue、API 和定时派单：增加重复任务与多写入者风险，暂不采用。
